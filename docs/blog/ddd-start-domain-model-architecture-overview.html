DDD START! 정리 — 도메인 모델부터 아키텍처 개요까지 (Chapter 1-2)

왜 도메인 모델이 중요할까? 비즈니스 로직이 서비스 클래스, 컨트롤러, 유틸리티에 흩어져 있으면 어떤 일이 벌어지는지 경험해본 적이 있을 것이다. 규칙 하나를 바꾸려면 코드 여기저기를 뒤져야 하고, 바꾼 뒤에도 빠뜨린 곳이 없는지 불안하다. DDD는 이 문제를 **도메인 모델** 중심으로 풀어낸다. 1장과 2장에서 그 출발점을 잡는다. ## Chapter 1 — 도메인 모델 시작 ## 도메인이란 **도메인**은 소프트웨어로 해결하려는 문제 영역 그 자체다. 온라인 서점을 만든다면 주문, 회원, 결제, 배송, 카탈로그, 리뷰 같은 것들이 하위 도메인이 된다. 이 하위 도메인들이 서로 맞물려야 비로소 하나의 서비스가 완성된다. **도메인 모델**은 이 문제 영역을 개념적으로 표현한 것이다. 클래스 다이어그램이 될 수도 있고, 상태 다이어그램이 될 수도 있다. 중요한 건 형식이 아니라, 도메인의 핵심 개념과 규칙을 담고 있느냐다. ## 도메인 모델 패턴 애플리케이션은 보통 네 개의 계층으로 나뉜다: - **표현(Presentation)**: 사용자의 요청을 받고, 결과를 보여준다 - **응용(Application)**: 기능을 실행한다. 단, 로직을 직접 구현하지 않고 도메인 계층에 위임한다 - **도메인(Domain)**: 비즈니스 규칙을 구현한다 - **인프라스트럭처(Infrastructure)**: DB, 메시징, 외부 API 같은 기술적 세부사항을 처리한다 핵심은 **비즈니스 규칙이 도메인 모델 안에만 있어야 한다**는 것이다. 규칙이 바뀌면 도메인 모델만 고치면 된다. 다른 계층은 건드릴 필요가 없다. public class Order { private OrderState state; private ShippingInfo shippingInfo; public void changeShippingInfo(ShippingInfo newShippingInfo) { if (!state.isShippingChangeable()) { throw new IllegalStateException( "can't change shipping in " + state); } this.shippingInfo = newShippingInfo; } } public enum OrderState { PAYMENT_WAITING { public boolean isShippingChangeable() { return true; } }, PREPARING { public boolean isShippingChangeable() { return true; } }, SHIPPED, DELIVERING, DELIVERY_COMPLETED; public boolean isShippingChangeable() { return false; } } "결제 대기 중이거나 상품 준비 중일 때만 배송지를 변경할 수 있다"는 도메인 규칙이 `OrderState` 안에 들어 있다. 이 규칙이 컨트롤러나 서비스 클래스에 흩어져 있었다면, 나중에 규칙이 바뀔 때 어디를 고쳐야 할지 찾기부터 힘들었을 것이다. ## 도메인 모델 도출 모델은 요구사항에서 점진적으로 뽑아낸다. 온라인 서점의 주문을 예로 들면: - 최소 한 종류 이상의 상품을 주문해야 한다 - 한 상품을 한 개 이상 주문할 수 있다 - 총 주문 금액은 각 상품의 구매 가격 합을 모두 더한 금액이다 - 주문할 때 배송지 정보를 반드시 지정해야 한다 - 출고를 하면 배송지 정보를 변경할 수 없다 - 출고 전에 주문을 취소할 수 있다 이 요구사항을 읽다 보면 `Order`, `OrderLine`, `ShippingInfo` 같은 개념이 자연스럽게 떠오른다: public class OrderLine { private Product product; private int price; private int quantity; private int amounts; public OrderLine(Product product, int price, int quantity) { this.product = product; this.price = price; this.quantity = quantity; this.amounts = calculateAmounts(); } private int calculateAmounts() { return price * quantity; } } ## 엔티티와 밸류 도메인 모델은 크게 **엔티티**와 **밸류**로 구성된다. **엔티티(Entity)**는 **식별자**를 가진다. 주문번호가 같으면 같은 주문이고, 회원 ID가 같으면 같은 회원이다. 식별자는 규칙 기반 생성(날짜 + 일련번호), UUID, 직접 입력(이메일), DB 시퀀스 등 여러 방식으로 만들 수 있다. public class Order { private String orderNumber; @Override public boolean equals(Object obj) { if (this == obj) return true; if (obj == null) return false; if (obj.getClass() != Order.class) return false; Order other = (Order) obj; if (this.orderNumber == null) return false; return this.orderNumber.equals(other.orderNumber); } } **밸류(Value)**는 식별자 없이, 개념적으로 하나인 속성을 표현한다. `ShippingInfo` 안에 있는 받는 사람 정보와 주소 정보를 각각 밸류 타입으로 분리하면 의미가 훨씬 명확해진다: public class Receiver { private String name; private String phoneNumber; } public class Address { private String address1; private String address2; private String zipcode; } `int price`라고 쓰면 이게 원화인지 달러인지, 세전인지 세후인지 알 수 없다. 하지만 `Money`라는 밸류 타입을 만들면 의미가 분명해진다: public class Money { private int value; public Money add(Money money) { return new Money(this.value + money.value); } public Money multiply(int multiplier) { return new Money(value * multiplier); } } 여기서 주목할 점은 `add()` 메서드가 기존 값을 바꾸지 않고 **새로운 Money 객체를 리턴**한다는 것이다. 밸류 타입은 **불변(Immutable)**으로 구현하는 게 좋다. 참조 투명성과 스레드 안전을 보장할 수 있기 때문이다. ## set 메서드를 넣지 않는 이유 도메인 모델에 `set` 메서드를 무조건 넣는 건 나쁜 습관이다. `set`은 도메인의 의도를 코드에서 지워버린다. `setShippingInfo()` — 그냥 배송지 값을 세팅한다는 뜻 `changeShippingInfo()` — 배송지 정보를 **변경**한다는 도메인 의도가 드러남 불변 밸류 타입을 사용하면 자연스럽게 `set` 메서드를 만들 이유가 없어진다. ## 유비쿼터스 언어 도메인에서 쓰는 용어를 코드에 그대로 반영해야 한다. 에릭 에반스는 이를 **유비쿼터스 언어(Ubiquitous Language)**라고 불렀다. // 나쁜 예 — 이름만 보면 뭘 뜻하는지 모른다 public enum OrderState { STEP1, STEP2, STEP3, STEP4, STEP5, STEP6 } // 좋은 예 — 코드를 읽는 것만으로 상태가 뭔지 알 수 있다 public enum OrderState { PAYMENT_WAITING, PREPARING, SHIPPED, DELIVERING, DELIVERY_COMPLETED, CANCELED } 기획자, 도메인 전문가, 개발자가 **같은 언어**로 이야기하면 소통의 모호함이 줄어든다. 코드가 곧 문서가 되는 셈이다. ## Chapter 2 — 아키텍처 개요 ## 네 개의 영역 1장에서 살펴본 네 계층을 좀 더 구체적으로 들여다보자. **표현 영역**은 사용자의 요청을 받아 응용 영역에 전달하고, 처리 결과를 다시 사용자에게 보여준다. 스프링 MVC의 컨트롤러가 대표적이다. **응용 영역**은 기능을 실행하되, 로직을 직접 수행하지 않고 도메인 모델에 위임한다: public class CancelOrderService { @Transactional public void cancelOrder(String orderId) { Order order = findOrderById(orderId); if (order == null) throw new OrderNotFoundException(orderId); order.cancel(); // 도메인 모델에 위임 } } `cancelOrder()`는 직접 취소 로직을 구현하지 않는다. `order.cancel()`을 호출할 뿐이다. 취소할 수 있는 조건, 취소 시 상태 변경 같은 규칙은 모두 `Order` 안에 있다. **도메인 영역**은 배송지 변경, 결제 완료, 주문 총액 계산 같은 핵심 비즈니스 로직이 사는 곳이다. **인프라스트럭처 영역**은 RDBMS 연동, 메시징 큐, 메일 발송, 외부 API 호출 등 기술적 구현을 담당한다. ## DIP (의존 역전 원칙) 계층 구조에서 한 가지 문제가 있다. 응용이나 도메인 계층이 인프라에 직접 의존하면, 인프라 기술이 바뀔 때 도메인까지 수정해야 한다. **DIP**는 이 문제를 해결한다. 고수준 모듈(도메인)에 인터페이스를 두고, 저수준 모듈(인프라)이 그 인터페이스를 구현하게 만든다: // 도메인에 인터페이스 정의 public interface RuleDiscounter { public Money applyRules(Customer customer, List orderLines); } // 인프라에서 구현 public class DroolsRuleDiscounter implements RuleDiscounter { @Override public Money applyRules(Customer customer, List orderLines) { // Drools 구현 } } // 응용 서비스는 인터페이스에만 의존 public class CalculateDiscountService { private RuleDiscounter ruleDiscounter; public CalculateDiscountService(RuleDiscounter ruleDiscounter) { this.ruleDiscounter = ruleDiscounter; } public Money calculateDiscount(OrderLine orderLines, String customerId) { Customer customer = findCustomer(customerId); return ruleDiscounter.applyRules(customer, orderLines); } } 여기서 핵심은 인터페이스를 **도메인 관점에서** 정의해야 한다는 것이다. `RuleEngine`(기술 관점)이 아니라 `RuleDiscounter`(할인 계산이라는 비즈니스 개념)로 이름을 짓는다. 이렇게 하면 Drools를 다른 룰 엔진으로 바꿔도 도메인과 응용 영역은 영향을 받지 않는다. 단, 모든 곳에서 DIP를 강제할 필요는 없다. 스프링의 `@Transactional`이나 JPA의 `@Entity`처럼 DIP의 장점을 해치지 않는 편의 기능은 실용적으로 사용하는 게 현명하다. ## 도메인 영역의 주요 구성요소 도메인 모델을 구성하는 핵심 요소 다섯 가지: - **엔티티(Entity)**: 식별자를 가진 객체. 자신만의 라이프사이클이 있다. Order, Member, Product - **밸류(Value)**: 식별자가 없는 객체. 개념적으로 하나인 속성을 표현한다. Address, Money - **애그리거트(Aggregate)**: 관련된 엔티티와 밸류를 하나로 묶은 것. Order + OrderLine + Orderer → '주문' 애그리거트 - **리포지터리(Repository)**: 도메인 객체를 저장하고 조회하는 역할 - **도메인 서비스(Domain Service)**: 특정 엔티티에 속하지 않는 도메인 로직. 여러 엔티티를 조합해야 하는 경우에 사용 ## 도메인 엔티티 vs DB 엔티티 흔히 혼동하는 부분이다. 도메인 모델의 엔티티와 DB의 엔티티는 **같지 않다.** 가장 큰 차이는, 도메인 엔티티는 데이터뿐 아니라 **도메인 기능**을 함께 제공한다는 것이다. 단순한 데이터 구조가 아니라, 규칙을 캡슐화해서 외부에서 데이터를 함부로 바꾸지 못하게 막는다: public class Order { private OrderNo number; private Orderer orderer; private ShippingInfo shippingInfo; public void changeShippingInfo(ShippingInfo newShippingInfo) { checkShippingInfoChangeable(); setShippingInfo(newShippingInfo); } private void setShippingInfo(ShippingInfo newShippingInfo) { if (newShippingInfo == null) throw new IllegalArgumentException(); this.shippingInfo = newShippingInfo; } } `setShippingInfo()`가 `private`인 것에 주목하자. 외부에서는 `changeShippingInfo()`를 통해서만 배송지를 바꿀 수 있고, 이 메서드 안에서 변경 가능 여부를 검사한다. ## 애그리거트와 리포지터리 도메인이 커지면 엔티티와 밸류가 늘어나면서 모델이 복잡해진다. 이때 관련된 객체들을 상위 수준에서 묶어주는 것이 **애그리거트**다. 주문이라는 개념은 Order, OrderLine, Orderer, ShippingInfo 등 여러 객체로 구성되지만, 이걸 '주문 애그리거트'로 묶으면 전체 구조가 한눈에 들어온다. 애그리거트에는 **루트 엔티티**가 있다. 외부에서는 루트를 통해서만 애그리거트 안의 객체에 접근한다: public class Order { // 애그리거트 루트 public void changeShippingInfo(ShippingInfo newInfo) { checkShippingInfoChangeable(); this.shippingInfo = newInfo; } } 도메인 객체를 영구 보관하려면 **리포지터리**가 필요하다. 리포지터리 인터페이스는 **도메인 영역**에, 구현 클래스는 **인프라 영역**에 둔다: public interface OrderRepository { public Order findByNumber(OrderNumber number); public void save(Order order); public void delete(Order order); } 응용 서비스는 리포지터리를 통해 도메인 객체를 구하고, 도메인 기능을 실행한다: public class CancelOrderService { private OrderRepository orderRepository; @Transaction public void cancel(OrderNumber number) { Order order = orderRepository.findByNumber(number); if (order == null) throw new NoOrderException(number); order.cancel(); } } ## 요청 처리 흐름 전체 흐름을 한눈에 정리하면: 1. 브라우저 → Controller: HTTP 요청 2. Controller → App Service: 요청 데이터를 변환해서 전달 3. App Service → Repository: 도메인 객체를 조회 4. App Service → Domain Object: 도메인 로직 실행 5. Controller → 브라우저: HTTP 응답 ## 모듈 구성 도메인이 크면 하위 도메인별로 패키지를 나누고, 각각 네 개의 영역을 갖도록 구성한다: com.myshop ├── catalog │ ├── ui / application / domain / infrastructure ├── order │ ├── ui / application / domain / infrastructure └── member ├── ui / application / domain / infrastructure `domain` 패키지 안에서는 애그리거트 기준으로 다시 나눈다. 한 패키지에 타입이 10개를 넘기면 분리를 고려해볼 시점이다. ## 정리 - **도메인 모델 패턴**: 핵심 규칙은 도메인에만 둔다. 응용 서비스는 위임만 한다 - **엔티티 vs 밸류**: 엔티티는 식별자로 구분하고, 밸류는 불변으로 만들어 의미를 명확히 한다 - **DIP**: 인터페이스를 도메인에 정의해서, 인프라 기술이 바뀌어도 도메인에 영향이 없게 한다 - **애그리거트**: 관련 객체를 하나로 묶고, 루트 엔티티를 통해서만 접근한다 - **리포지터리**: 인터페이스는 도메인에, 구현은 인프라에 둔다 - **유비쿼터스 언어**: 도메인 용어를 코드에 그대로 반영한다. 코드가 곧 문서가 된다
