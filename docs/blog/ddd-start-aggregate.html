DDD START! 정리 — 애그리거트, 경계와 루트 그리고 트랜잭션 (Chapter 3)

Order, OrderLine, ShippingInfo, Orderer, PaymentInfo... 도메인 객체가 수십 개가 되면 개별 객체 수준에서 전체 구조를 파악하는 건 거의 불가능하다. 이때 관련된 객체들을 상위 수준에서 묶어서 보면 비로소 관계가 눈에 들어온다. 이 "묶음"이 바로 **애그리거트(Aggregate)**다. ## 애그리거트란 쉽게 말해, 관련된 객체를 하나의 군집으로 묶은 것이다. 온라인 쇼핑몰을 예로 들면: - **주문 애그리거트**: Order, OrderLine, ShippingInfo, Orderer - **상품 애그리거트**: Product, Category - **회원 애그리거트**: Member, MemberGrade - **결제 애그리거트**: PaymentInfo 이렇게 묶어놓으면 "주문은 상품을 참조하고, 회원이 주문을 한다"는 식으로 도메인 간 관계가 단순해진다. 복잡도가 낮아지니 기능을 확장하거나 변경할 때 필요한 노력도 줄어든다. ## 경계를 어디에 그을 것인가 한 애그리거트에 속한 객체는 다른 애그리거트에 속하지 않는다. 경계를 정하는 기준은 **"함께 생성되고, 함께 변경되는가"**다. 주문할 때 상품 개수, 배송지 정보, 주문자 정보는 주문 시점에 함께 만들어지므로 한 애그리거트에 속한다. 그런데 "A가 B를 갖는다"는 요구사항이 있다고 해서 반드시 한 애그리거트는 아니다. Product와 Review가 대표적이다. 상품 페이지에 리뷰가 함께 보이지만: - 함께 생성되지 않고, 함께 변경되지도 않는다 - 변경 주체가 다르다 — Product는 상품 담당자, Review는 고객 - 서로의 변경이 상대에게 영향을 주지 않는다 따라서 Product와 Review는 **서로 다른 애그리거트**다. ## 애그리거트 루트 애그리거트 안의 객체들이 일관된 상태를 유지하려면, 전체를 관리하는 주체가 필요하다. 이 역할을 맡는 것이 **애그리거트 루트 엔티티**다. 주문 애그리거트에서 루트는 `Order`다. OrderLine, ShippingInfo, Orderer는 모두 Order를 통해서만 접근한다. public class Order { public void changeShippingInfo(ShippingInfo newShippingInfo) { verifyNotYetShipped(); setShippingInfo(newShippingInfo); } private void verifyNotYetShipped() { if (state != OrderState.PAYMENT_WAITING && state != OrderState.WAITING) throw new IllegalStateException("aleady shipped"); } } "배송이 시작되기 전까지만 배송지를 변경할 수 있다"는 규칙이 `changeShippingInfo()` 안에 녹아 있다. 배송지를 바꾸고 싶으면 반드시 `Order`를 거쳐야 하므로, 이 규칙을 우회할 방법이 없다. ## 루트를 거치지 않으면 생기는 문제 애그리거트 내부 객체를 직접 꺼내서 수정하면 어떻게 될까? ShippingInfo si = order.getShippingInfo(); si.setAddress(newAddress); 이 코드는 주문 상태와 상관없이 배송지를 바꿔버린다. 루트가 강제하는 규칙을 완전히 무시하는 것이다. DB에서 직접 UPDATE를 때리는 것과 다를 바 없다. 이런 문제를 원천 차단하려면 두 가지를 습관처럼 지켜야 한다: - 단순히 필드를 바꾸는 public set 메서드를 만들지 않는다 - 밸류 타입은 불변으로 구현한다 ## 밸류를 불변으로 만드는 이유 public set 메서드의 문제는 도메인의 의도가 드러나지 않는다는 것이다. `setOrderState()` 대신 `cancel()`이나 `changePassword()`처럼 의미가 드러나는 이름을 써야 한다. 여기서 한 발 더 나아가 밸류를 불변으로 만들면, 루트를 통하지 않고는 값을 바꿀 수가 없게 된다: ShippingInfo si = order.getShippingInfo(); si.setAddress(newAddress); // 불변이면 컴파일 에러! 값을 바꾸고 싶다면 새로운 밸류 객체를 만들어서 루트의 메서드에 전달하는 수밖에 없다: public class Order { private ShippingInfo shippingInfo; public void changeShippingInfo(ShippingInfo newShippingInfo) { verifyNotYetShipped(); setShippingInfo(newShippingInfo); } private void setShippingInfo(ShippingInfo newShippingInfo) { this.shippingInfo = newShippingInfo; } } `setShippingInfo()`가 `private`인 것에 주목하자. 외부에서는 `changeShippingInfo()`만 호출할 수 있고, 그 안에서 배송 상태 검증이 먼저 실행된다. ## 루트가 내부 객체를 조합하는 방식 애그리거트 루트는 내부 객체들을 조합해서 기능을 완성한다. 총 주문 금액 계산이 좋은 예다: public class Order { private Money totalAmounts; private List orderLines; private void calculateTotalAmounts() { int sum = orderLines.stream() .mapToInt(ol -> ol.getPrice() * ol.quantity()) .sum(); this.totalAmounts = new Money(sum); } } OrderLine 목록을 별도 클래스로 분리해서 계산을 위임할 수도 있다: public class Order { private OrderLines orderLines; public void changeOrderLines(List newLines) { orderLines.changeOrderLines(newLines); this.totalAmounts = orderLines.getTotalAmounts(); } } 여기서 한 가지 주의할 점이 있다. `getOrderLines()`로 OrderLines를 외부에 노출하면, 외부에서 직접 `lines.changeOrderLines()`를 호출해 totalAmounts와 불일치가 생길 수 있다. 이 문제도 OrderLines를 불변으로 구현하면 해결된다. ## 트랜잭션 범위 트랜잭션은 작을수록 좋다. 원칙은 간단하다: **한 트랜잭션에서는 한 개의 애그리거트만 수정한다.** 주문 애그리거트에서 회원 애그리거트의 주소를 함께 바꾸는 건 안 된다: public class Order { private Orderer orderer; public void shipTo(ShippingInfo newShippingInfo, boolean useNewShippingAddrAsMemberAddr) { verifyNotYetShipped(); setShippingInfo(newShippingInfo); if (useNewShippingAddrAsMemberAddr) { // 다른 애그리거트를 수정하면 안 됨! orderer.getCustomer().changeAddress(newShippingInfo.getAddress()); } } } 꼭 두 개 이상의 애그리거트를 한 트랜잭션으로 수정해야 한다면, 그건 응용 서비스에서 처리해야 한다. 애그리거트 안에서 다른 애그리거트를 건드리면 결합도가 높아진다. ## ID로 다른 애그리거트를 참조하기 애그리거트끼리 필드로 직접 참조하면 편하지만, 세 가지 문제가 생긴다: - **편한 탐색의 오용**: 다른 애그리거트의 상태를 너무 쉽게 바꿀 수 있다 - **성능 고민**: 즉시 로딩과 지연 로딩 사이에서 끊임없이 고민해야 한다 - **확장의 어려움**: 하위 도메인마다 다른 DB를 쓸 수 있는데, 객체 참조는 같은 DB를 전제한다 이 문제들을 해결하는 방법이 **ID 참조**다: public class Orderer { private MemberId memberId; // Member 객체 대신 ID로 참조 private String name; } ID 참조를 쓰면 애그리거트 간 경계가 명확해지고, 결합도가 낮아지며, 서로 다른 기술을 사용하는 것도 가능해진다. ## N+1 조회 문제 ID 참조의 단점은 여러 애그리거트를 한꺼번에 읽어야 할 때 조회 성능이 떨어질 수 있다는 것이다. 주문 10건을 조회하면서 각 주문의 상품 정보를 따로 로딩하면, 1 + 10 = 11번의 쿼리가 나간다. 이것이 N+1 문제다. 해결책은 조인을 쓰는 것이다. 조회 전용 DAO를 만들고 세타 조인으로 한 번에 가져온다: @Repository public class JpaOrderViewDao implements OrderViewDao { @Override public List selectByOrderer(String ordererId) { String selectQuery = "select new com.myshop.order.application.dto.OrderView(o, m, p) "+ "from Order o join o.orderLines ol, Member m, Product p " + "where o.orderer.memberId.id = :ordererId " + "and o.orderer.memberId = m.id "+ "and ol.productId = p.id "+ "order by o.number.number desc"; // ... } } 즉시 로딩이니 지연 로딩이니 고민할 필요 없이, 조회 화면에 필요한 데이터를 한 방 쿼리로 가져올 수 있다. ## 집합 연관 — 1:N과 M:N 1:N 연관에서 주의할 점이 있다. 카테고리와 상품의 관계가 개념적으로는 1:N이지만, 카테고리에 속한 모든 상품을 컬렉션으로 들고 있으면 성능이 심각하게 나빠진다. 실제로는 상품 쪽에서 카테고리를 참조하는 N:1로 구현한다: public class Product { private CategoryId category; } M:N 연관도 마찬가지다. 양방향으로 컬렉션을 가질 필요 없이, 필요한 쪽에서 단방향 M:N만 적용하면 된다. RDBMS에서는 조인 테이블로 구현한다. ## 애그리거트를 팩토리로 사용하기 상점이 차단(blocked) 상태일 때 상품 등록을 막는 기능을 어디에 구현할까? // 도메인 로직이 응용 서비스에 노출되는 안 좋은 예 public class RegisterProductService { public ProductId registerNewProduct(NewProductRequest req) { Store account = accountRepository.findStoreById(req.getStoreId()); checkNull(account); if (account.isBlocked()) { throw new StoreBlockedException(); } ProductId id = productRepository.nextId(); Product product = new Product(id, account.getId(), ...); productRepository.save(product); return id; } } "차단된 상점은 상품을 등록할 수 없다"는 도메인 규칙인데, 응용 서비스에 구현되어 있다. 이 로직은 Store 애그리거트 안에 있어야 한다: public class Store extends Member { public Product createProduct(ProductId newProductId, ...생략) { if (isBlocked()) throw new StoreBlockedException(); return new Product(newProductId, getId(), ...생략); } } 이제 응용 서비스는 Store의 상태를 직접 확인할 필요가 없다. Store가 스스로 "나는 차단되었으니 상품을 못 만든다"고 판단한다. 도메인 로직이 한 곳에 모이고, 응집도가 높아진다. 이것이 **애그리거트를 팩토리로 사용**하는 패턴이다.
