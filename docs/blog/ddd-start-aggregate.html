DDD START! 정리 — 애그리거트, 경계와 루트 그리고 트랜잭션 (Chapter 3)

도메인 모델이 복잡해지면 개별 객체 수준에서는 전체 구조를 파악하기 어렵다. 주문, 배송지, 주문자, 결제 같은 객체들이 얽혀 있을 때 상위 수준에서 묶어서 봐야 관계가 보인다. 이 "묶음"이 바로 **애그리거트(Aggregate)**다. 3장 핵심 내용을 정리한다. ## 애그리거트란 관련된 객체를 하나의 군(群)으로 묶은 것이다. 상위 수준에서 모델을 정리하면 도메인 간 관계를 단순하게 파악할 수 있다. 예를 들어 온라인 쇼핑몰 도메인을 보면: - **주문 애그리거트**: Order, OrderLine, ShippingInfo, Orderer - **상품 애그리거트**: Product, Category - **회원 애그리거트**: Member, MemberGrade - **결제 애그리거트**: PaymentInfo 복잡도가 낮아지니 도메인 기능을 확장하고 변경하는 데 필요한 노력도 줄어든다. ## 애그리거트 경계 설정 한 애그리거트에 속한 객체는 다른 애그리거트에 속하지 않는다. 각 애그리거트는 독립된 객체 군이며, 자기 자신만 관리할 뿐 다른 애그리거트를 관리하지 않는다. 경계를 설정할 때 기본이 되는 건 **도메인 규칙과 요구사항**이다. 함께 생성되는 구성요소는 한 애그리거트에 속할 가능성이 높다. 예를 들어 주문할 때 상품 개수, 배송지 정보, 주문자 정보는 주문 시점에 함께 생성되므로 한 애그리거트에 속한다. 주의할 점: "A가 B를 갖는다"는 요구사항이 있다고 해서 반드시 한 애그리거트에 속하는 건 아니다. Product와 Review를 생각해 보자. 상품 상세 페이지에 리뷰가 함께 보이지만: - 함께 생성되지 않고, 함께 변경되지도 않는다 - 변경 주체가 다르다 (Product는 상품 담당자, Review는 고객) - 서로의 변경이 영향을 주지 않는다 따라서 Product와 Review는 **서로 다른 애그리거트**에 속한다. ## 애그리거트 루트 애그리거트에 속한 모든 객체가 일관된 상태를 유지하려면 전체를 관리할 주체가 필요하다. 이 책임을 지는 것이 바로 **애그리거트 루트 엔티티**다. 주문 애그리거트에서 루트 역할을 하는 엔티티는 `Order`이다. OrderLine, ShippingInfo, Orderer 등은 Order에 직접 또는 간접적으로 속한다. public class Order { // 애그리거트 루트가 도메인 규칙을 구현한 기능을 제공한다. public void changeShippingInfo(ShippingInfo newShippingInfo) { verifyNotYetShipped(); setShippingInfo(newShippingInfo); } private void verifyNotYetShipped() { if (state != OrderState.PAYMENT_WAITING && state != OrderState.WAITING) throw new IllegalStateException("aleady shipped"); } } 애그리거트 루트가 제공하는 메서드는 도메인 규칙에 따라 애그리거트에 속한 객체의 일관성이 깨지지 않도록 구현해야 한다. 예를 들어, 배송이 시작되기 전까지만 배송지 정보를 변경할 수 있다는 규칙이 있다면, `changeShippingInfo()` 메서드는 이 규칙에 따라 배송 시작 여부를 확인하고 변경이 가능한 경우에만 배송지 정보를 변경한다. ## 루트가 아닌 객체를 직접 변경하면 안 되는 이유 애그리거트 루트가 아닌 다른 객체가 애그리거트에 속한 객체를 직접 변경하면 안 된다. 이는 애그리거트 루트가 강제하는 규칙을 적용할 수 없어 모델의 일관성을 깨는 원인이 된다. // 이렇게 하면 안 된다! ShippingInfo si = order.getShippingInfo(); si.setAddress(newAddress); 이 코드는 주문 상태에 상관없이 배송지 주소를 변경할 수 있는데, 이는 업무 규칙을 무시하고 DB 테이블에서 직접 데이터를 수정하는 것과 같은 결과를 만든다. 불필요한 중복을 피하고 애그리거트 루트를 통해서만 도메인 로직을 구현하게 만들려면 두 가지를 습관적으로 적용해야 한다: - 단순히 필드를 변경하는 public set 메서드를 만들지 않는다 - 밸류 타입은 불변으로 구현한다 ## 밸류와 불변, 그리고 일관성 공개 set 메서드는 중요한 도메인의 의미나 의도를 표현하지 못하고 도메인 로직이 응용 영역이나 표현 영역으로 분산되게 만드는 원인이 된다. set 형식의 이름 대신 `cancel`이나 `changePassword`처럼 의미가 더 잘 드러나는 이름을 사용하는 빈도가 높아진다. 공개 set을 만들지 않는 것의 연장으로 밸류는 불변 타입으로 구현한다. 밸류 객체의 값을 변경할 수 없으면 애그리거트 루트에서 밸류 객체를 구해도 값을 변경할 수 없다. ShippingInfo si = order.getShippingInfo(); si.setAddress(newAddress); // ShippingInfo 밸류 객체가 불변이면, 이 코드는 컴파일 에러! 밸류가 불변이면 밸류 객체의 값을 변경하는 방법은 새로운 밸류 객체를 할당하는 것뿐이다. 즉, 애그리거트 루트가 제공하는 메서드에 새로운 밸류 객체를 전달해서 값을 변경하는 방법밖에 없다. public class Order { private ShippingInfo shippingInfo; public void changeShippingInfo(ShippingInfo newShippingInfo) { verifyNotYetShipped(); setShippingInfo(newShippingInfo); } // set 메서드의 접근 허용 범위는 private이다. private void setShippingInfo(ShippingInfo newShippingInfo) { // 밸류가 불변이므로, 새로운 객체를 할당해서 값을 변경해야 한다. this.shippingInfo = newShippingInfo; } } ## 애그리거트 루트의 기능 구현 애그리거트 루트는 애그리거트 내부의 다른 객체를 조합해서 기능을 완성한다. public class Order { private Money totalAmounts; private List orderLines; private void calculateTotalAmounts() { int sum = orderLines.stream() .mapToInt(ol -> ol.getPrice() * ol.quantity()) .sum(); this.totalAmounts = new Money(sum); } } 기능 실행을 위임하기도 한다. OrderLine 목록을 별도 클래스로 분리했다면: public class Order { private OrderLines orderLines; public void changeOrderLines(List newLines) { orderLines.changeOrderLines(newLines); this.totalAmounts = orderLines.getTotalAmounts(); } } 이때 주의할 점: Order가 `getOrderLines()`로 OrderLines를 외부에 노출하면, 외부에서 `lines.changeOrderLines(newOrderLines)` 같은 코드를 실행해 Order의 totalAmounts와 불일치가 생기는 버그를 만들 수 있다. 이런 버그를 방지하려면 외부에서 OrderLine 목록을 변경할 수 없도록 OrderLines를 불변으로 구현하면 된다. ## 트랜잭션 범위 트랜잭션 범위는 작을수록 좋다. 한 트랜잭션에서는 **한 개의 애그리거트만 수정**해야 한다. 한 애그리거트에서 다른 애그리거트를 수정하면 결합도가 높아진다. 예를 들어, 주문 애그리거트에서 회원 애그리거트의 주소를 함께 변경하면 안 된다. public class Order { private Orderer orderer; public void shipTo(ShippingInfo newShippingInfo, boolean useNewShippingAddrAsMemberAddr) { verifyNotYetShipped(); setShippingInfo(newShippingInfo); if (useNewShippingAddrAsMemberAddr) { // 다른 애그리거트의 상태를 변경하면 안 됨! orderer.getCustomer().changeAddress(newShippingInfo.getAddress()); } } } 부득이하게 한 트랜잭션으로 두 개 이상의 애그리거트를 수정해야 한다면 응용 서비스에서 두 애그리거트를 수정하도록 구현해야 한다. ## ID를 이용한 애그리거트 참조 한 객체가 다른 객체를 참조하는 것처럼 애그리거트도 다른 애그리거트를 참조한다. 애그리거트 간 참조는 필드를 통해 쉽게 구현할 수 있다. 주문 애그리거트에 속해 있는 Orderer는 주문한 회원을 참조하기 위해 회원 애그리거트 루트인 Member를 필드로 참조할 수 있다. 하지만 필드를 이용한 애그리거트 참조는 다음의 문제를 야기할 수 있다: - **편한 탐색 오용**: 다른 애그리거트의 상태를 쉽게 변경할 수 있게 됨 - **성능에 대한 고민**: 즉시 로딩 vs 지연 로딩 결정 - **확장 어려움**: 하위 도메인마다 다른 DBMS를 사용할 수 있음 이 세 가지 문제를 완화할 때 사용할 수 있는 것이 **ID를 이용해서 다른 애그리거트를 참조**하는 것이다. public class Order { private Orderer orderer; // ... } public class Orderer { private MemberId memberId; // Member 객체 대신 ID로 참조 private String name; } ID 참조를 사용하면: - 모든 객체가 참조로 연결되지 않고 한 애그리거트에 속한 객체들만 참조로 연결된다 - 애그리거트의 경계를 명확히 하고 물리적 연결을 제거해 모델의 복잡도를 낮춘다 - 다른 애그리거트를 직접 참조하지 않으므로 결합도를 낮출 수 있다 - 애그리거트별로 다른 구현 기술을 사용하는 것도 가능해진다 ## N+1 조회 문제와 해결 다른 애그리거트를 ID로 참조하면 여러 애그리거트를 읽어야 할 때 조회 속도가 문제될 수 있다. // 주문마다 상품과 회원 애그리거트를 읽어오는 코드 // 주문 개수가 10개면 1번의 쿼리와 주문별로 각 상품 정보 로딩 = 10번 쿼리 // 이것이 N+1 조회 문제다. 해결 방법은 조인을 사용하는 것이다. 데이터 조회를 위한 별도 DAO를 만들고 세타 조인으로 한 번의 쿼리로 필요한 데이터를 로딩하면 된다. @Repository public class JpaOrderViewDao implements OrderViewDao { @Override public List selectByOrderer(String ordererId) { String selectQuery = "select new com.myshop.order.application.dto.OrderView(o, m, p) "+ "from Order o join o.orderLines ol, Member m, Product p " + "where o.orderer.memberId.id = :ordererId " + "and o.orderer.memberId = m.id "+ "and ol.productId = p.id "+ "order by o.number.number desc"; // ... } } JPQL은 Order, Member, Product 애그리거트를 세타 조인으로 한 번의 쿼리로 로딩한다. 즉시 로딩이나 지연 로딩 같은 로딩 전략을 고민할 필요 없이 조회 화면에서 필요한 애그리거트 데이터를 한 번의 쿼리로 로딩할 수 있다. ## 애그리거트 간 집합 연관 1:N 연관 — 예를 들어 카테고리와 상품의 관계에서, 개념적으로는 1:N이지만 실제 구현에서 카테고리에 속한 모든 Product를 로딩하면 성능 문제가 심각해진다. 실제로는 상품에서 카테고리로의 N:1 연관으로 구현한다. public class Product { private CategoryId category; // ... } M:N 연관 — 개념적으로는 양쪽 애그리거트에 컬렉션으로 연관을 만든다. 하지만 실제 구현에서는 상품에서 카테고리로의 단방향 M:N 연관만 적용하면 되는 것이다. RDBMS를 이용해서 구현하려면 조인 테이블을 사용한다. ## 애그리거트를 팩토리로 사용하기 온라인 쇼핑몰에서 고객이 여러 차례 신고를 해서 특정 상점이 더 이상 물건을 등록하지 못하도록 차단한 상태라고 해보자. // 도메인 로직이 응용 서비스에 노출되는 안 좋은 예 public class RegisterProductService { public ProductId registerNewProduct(NewProductRequest req) { Store account = accountRepository.findStoreById(req.getStoreId()); checkNull(account); if (account.isBlocked()) { throw new StoreBlockedException(); } ProductId id = productRepository.nextId(); Product product = new Product(id, account.getId(), ...); productRepository.save(product); return id; } } Store가 Product를 생성할 수 있는지 여부를 판단하고 Product를 생성하는 것은 논리적으로 하나의 도메인 기능인데 이 도메인 기능을 응용 서비스에서 구현하고 있다. 이 기능을 구현하기에 더 좋은 장소는 Store 애그리거트이다. public class Store extends Member { public Product createProduct(ProductId newProductId, ...생략) { if (isBlocked()) throw new StoreBlockedException(); return new Product(newProductId, getId(), ...생략); } } 이제 응용 서비스에서 더 이상 Store의 상태를 확인하지 않아도 된다. Product 생성 가능 여부를 확인하는 도메인 로직은 Store에서 구현하고 있다. 도메인의 응집도도 높아졌다. 이것이 바로 **애그리거트를 팩토리로 사용**할 때 얻을 수 있는 장점이다.
