DDD START! 정리 — 리포지터리와 모델 구현, JPA 매핑 전략 (Chapter 4)

3장까지는 도메인 모델을 개념적으로 설계했다면, 4장부터는 그걸 실제 코드로 만드는 단계다. JPA를 이용해 리포지터리를 구현하고, 엔티티와 밸류를 DB 테이블에 매핑하는 구체적인 전략을 살펴본다. ## 리포지터리는 어디에 두는가 리포지터리 인터페이스는 애그리거트와 함께 **도메인 영역**에 둔다. 구현 클래스는 **인프라스트럭처 영역**에 둔다. 2장에서 다룬 DIP 그대로다. 도메인이 인프라에 의존하지 않고, 인프라가 도메인의 인터페이스를 구현한다. ## 기본 기능 — 조회와 저장 리포지터리가 제공하는 가장 기본적인 기능은 두 가지다: public interface OrderRepository { public Order findById(OrderNo no); public void save(Order order); } JPA의 EntityManager를 이용해 구현하면 이렇게 된다: @Repository public class JpaOrderRepository implements OrderRepository { @PersistenceContext private EntityManager entityManager; @Override public Order findById(OrderNo id) { return entityManager.find(Order.class, id); } @Override public void save(Order order) { entityManager.persist(order); } } 한 가지 편한 점이 있다. 수정용 `update()` 메서드는 만들 필요가 없다. JPA는 트랜잭션 범위 안에서 변경된 데이터를 커밋 시점에 자동으로 DB에 반영한다: @Transactional public void changeShippingInfo(OrderNo no, ShippingInfo newShippingInfo) { Order order = orderRepository.findById(no); if (order == null) throw new OrderNotFoundException(); order.changeShippingInfo(newShippingInfo); // 별도 save 호출 불필요 — 트랜잭션 커밋 시 자동 UPDATE } 삭제도 마찬가지로 리포지터리에 구현하지만, 실무에서는 물리 삭제보다 삭제 플래그를 쓰는 경우가 훨씬 많다. ## 엔티티와 밸류를 JPA에 매핑하기 매핑의 기본 규칙은 간단하다: - 애그리거트 루트 → `@Entity` - 루트에 속한 밸류 → `@Embeddable` - 밸류 타입 필드 → `@Embedded` 주문 애그리거트를 예로 들면, Order가 루트이고, Orderer와 ShippingInfo는 밸류다. 이 객체들은 하나의 테이블에 함께 매핑할 수 있다: @Entity @Table(name = "purchase_order") public class Order { // ... } Orderer는 밸류이므로 `@Embeddable`로 매핑한다: @Embeddable public class Orderer { @Embedded @AttributeOverrides( @AttributeOverride(name = "id", column = @Column(name = "orderer_id")) ) private MemberId memberId; @Column(name = "orderer_name") private String name; } `@AttributeOverrides`는 `@Embeddable`에 정의된 칼럼 이름과 실제 DB 칼럼 이름이 다를 때 사용한다. 여기서는 MemberId의 `id` 필드를 `orderer_id` 칼럼에 매핑하고 있다. ## 기본 생성자 — protected로 막는 이유 JPA는 DB에서 데이터를 읽어 객체를 생성할 때 기본 생성자를 사용한다. 그래서 `@Entity`와 `@Embeddable` 클래스에는 기본 생성자가 필요하다. 문제는 기본 생성자를 public으로 열어두면 불완전한 객체를 만들 수 있다는 것이다. 그래서 `protected`로 선언해서 JPA만 쓸 수 있게 막는다: @Embeddable public class Receiver { @Column(name = "receiver_name") private String name; @Column(name = "receiver_phone") private String phone; protected Receiver() {} // JPA 전용 public Receiver(String name, String phone) { this.name = name; this.phone = phone; } } ## 필드 접근 vs 프로퍼티 접근 JPA는 필드와 메서드(프로퍼티) 두 가지 방식으로 매핑할 수 있다. 프로퍼티 방식을 쓰면 get/set 메서드를 만들어야 하는데, 이게 문제를 일으킨다: @Entity @Access(AccessType.PROPERTY) public class Order { @Column(name = "state") @Enumerated(EnumType.STRING) public OrderState getState() { return state; } public void setState(OrderState state) { this.state = state; } } `setState()`가 public이면 외부에서 주문 상태를 마음대로 바꿀 수 있다. 3장에서 그토록 강조한 "루트를 통해서만 변경하라"는 원칙이 무너진다. 그래서 **필드 접근 방식**을 쓰는 게 낫다. 불필요한 get/set 메서드를 만들 필요가 없다: @Entity @Access(AccessType.FIELD) public class Order { @EmbeddedId private OrderNo number; @Column(name = "state") @Enumerated(EnumType.STRING) private OrderState state; // cancel(), changeShippingInfo() 등 도메인 기능만 제공 } ## AttributeConverter — 밸류를 단일 칼럼에 매핑 Money 밸류를 DB의 `total_amounts` 칼럼 하나에 매핑하고 싶다면? `@Embeddable`로는 안 되고, `AttributeConverter`를 사용해야 한다: @Converter(autoApply = true) public class MoneyConverter implements AttributeConverter { @Override public Integer convertToDatabaseColumn(Money money) { if (money == null) return null; else return money.getValue(); } @Override public Money convertToEntityAttribute(Integer value) { if (value == null) return null; else return new Money(value); } } `autoApply = true`로 설정하면 프로젝트 전체에서 Money 타입 필드에 이 컨버터가 자동 적용된다. ## 밸류 컬렉션은 별도 테이블에 Order가 여러 개의 OrderLine을 가질 때, 밸류 컬렉션은 별도 테이블에 저장한다: @Entity @Table(name = "purchase_order") public class Order { @ElementCollection @CollectionTable(name = "order_line", joinColumns = @JoinColumn(name = "order_number")) @OrderColumn(name = "line_idx") private List orderLines; } `@CollectionTable`의 `name`으로 밸류를 저장할 테이블을, `joinColumns`로 외래키 칼럼을 지정한다. ## 밸류로 만드는 식별자 `String orderId` 대신 `OrderNo`라는 밸류 타입으로 식별자를 만들면 의미가 더 명확해진다. 게다가 식별자에 기능을 추가할 수도 있다: @Embeddable public class OrderNo implements Serializable { @Column(name = "order_number") private String number; public boolean is2ndGeneration() { return number.startsWith("N"); } } 1세대 주문번호와 2세대 주문번호를 구분하는 기능을 식별자 자체에 넣을 수 있다. ## 별도 테이블의 밸류 — @SecondaryTable ARTICLE 테이블과 ARTICLE_CONTENT 테이블이 나뉘어 있다고 하자. ARTICLE_CONTENT는 자체 식별자가 필요해서 분리된 게 아니라, 단순히 데이터 구조 때문에 분리된 것이다. 그래서 ArticleContent는 엔티티가 아니라 **밸류**로 취급해야 한다. `@SecondaryTable`을 쓰면 밸류를 별도 테이블에 매핑할 수 있다: @Entity @Table(name = "article") @SecondaryTable( name = "article_content", pkJoinColumns = @PrimaryKeyJoinColumn(name = "id") ) public class Article { @Id private Long id; private String title; @AttributeOverrides({ @AttributeOverride(name = "content", column = @Column(table = "article_content")), @AttributeOverride(name = "contentType", column = @Column(table = "article_content")) }) private ArticleContent content; } ## 로딩 전략 — 즉시 vs 지연 애그리거트는 개념적으로 하나지만, 루트를 로딩할 때 모든 하위 객체를 한꺼번에 가져올 필요는 없다. Product가 Image 목록과 Option 목록을 갖고 있을 때 즉시 로딩을 쓰면, 세 테이블을 카타시안 조인하는 쿼리가 나간다. 결과에 중복이 생기고 성능이 나빠진다. 실제로 **상태를 변경하는 기능보다 조회하는 기능이 훨씬 더 자주 실행**된다. 지연 로딩을 쓸 때 추가 쿼리가 나가더라도, 그건 상태 변경 시에만 발생하므로 대부분의 경우 문제가 되지 않는다. 결론: 모든 연관을 즉시 로딩으로 설정할 필요 없다. **상황에 맞게 즉시/지연 로딩을 선택**한다. ## 영속성 전파 — cascade 애그리거트가 완전한 상태여야 한다는 원칙은 조회뿐 아니라 저장과 삭제에도 적용된다. 루트만 저장하고 하위 밸류는 안 저장하면 안 된다. `@Embeddable`은 자동으로 함께 저장/삭제되지만, `@Entity`로 매핑된 하위 객체는 cascade 설정이 필요하다: @OneToMany(cascade = {CascadeType.PERSIST, CascadeType.REMOVE}, orphanRemoval = true) @JoinColumn(name = "product_id") @OrderColumn(name = "list_idx") private List images = new ArrayList<>(); ## 식별자 생성 — 세 가지 방식 식별자를 만드는 방법은 크게 세 가지다: **1. 사용자가 직접 입력** — 이메일 주소처럼 사용자가 정하는 경우. 별도 생성 로직이 필요 없다. **2. 도메인 로직으로 생성** — 특정 규칙에 따라 조합하는 경우: public class OrderIdService { public OrderId createId(UserId userId) { if (userId == null) throw new IllegalArgumentException("invalid userid: " + userId); return new OrderId(userId.toString() + "-" + timestamp()); } private String timestamp() { return Long.toString(System.currentTimeMillis()); } } **3. DB 자동 증가 칼럼** — `@GeneratedValue`를 사용. 이 경우 객체를 저장하기 전에는 식별자를 알 수 없다: public class WriteArticleService { public Long write(NewArticleRequest req) { Article article = new Article("제목", new ArticleContent("content", "type")); articleRepository.save(article); // 이 시점에 식별자 생성 return article.getId(); // 저장 이후에야 사용 가능 } } JPA는 저장 시점에 생성된 식별자를 `@Id` 필드에 자동으로 할당해준다.
