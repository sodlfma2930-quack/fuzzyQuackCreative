SpeakingMax 백엔드 코드 읽기 가이드 — 파이썬 초보를 위한 DDD 4-Layer 해부

파이썬을 처음 접하면서 DDD(Domain-Driven Design) 기반 백엔드 프로젝트를 읽어야 하는 상황이라면, 이 글이 출발점이 될 수 있다. SpeakingMax 백엔드(wb-speakingmax-backend)의 구조를 처음부터 끝까지 풀어본다.

이 프로젝트가 뭐하는 건가

SpeakingMax는 영어 학습 앱이다. 이 레포는 그 앱의 백엔드(서버), 즉 앱 뒤에서 데이터를 저장하고 처리하는 프로그램이다. 현재 구현된 핵심 기능은 "보카(단어 학습)" 하나다. 학습 흐름은 3단계로 나뉜다. viewMode: 학습할 단어와 퀴즈 목록을 앱에 보내줌. viewFeedback: 사용자가 푼 퀴즈를 채점하고 점수와 경험치를 계산. viewSummary: 결과 요약 + 일일 미션 달성 여부 확인. 모든 학습 기록은 MySQL DB에 저장되고, 같은 셀을 반복 학습하는 부정행위도 감지한다.

파이썬 기본 개념 속성 정리

이 코드에서 자주 보이는 파이썬 문법을 최소한만 짚어본다. class (클래스) — "학생"이라는 개념을 코드로 표현한 것이 클래스다. 실제 학생 한 명 한 명은 이 설계도로 만든 인스턴스(객체)다. 
class Student:
    def __init__(self, name, score):
        self.name = name
        self.score = score

kim = Student("김철수", 85)
async / await — DB에서 데이터를 가져오는 건 시간이 걸린다. await은 "이거 기다리는 동안 다른 요청 먼저 처리해"라는 뜻이다. 이 프로젝트의 함수 대부분이 async def로 시작한다. @decorator — 함수 위에 @뭔가가 붙어 있으면 그 함수에 추가 기능을 입히는 것이다. @router.post("/mode")는 "이 함수는 POST /mode 요청이 오면 실행해"라는 뜻이다. from A import B — 다른 파일에 있는 코드를 가져다 쓰는 방법이다. from src.config import get_settings는 "src 폴더의 config.py에서 get_settings 함수를 가져와"라는 뜻이다. 타입 힌트 (name: str, -> int) — 변수 뒤에 : str 같은 건 "이 변수는 문자열이야"라고 알려주는 표시다. 실행에는 영향 없지만 코드를 읽기 쉽게 만든다.

4개 층(Layer) 구조 이해하기

이 프로젝트는 코드를 4개의 층으로 나눠 놓았다. 식당에 비유하면 이렇다. Presentation (src/presentation/) — 카운터 직원. 손님(앱)의 주문을 받고, 완성된 음식을 예쁘게 포장해서 전달한다. HTTP 요청을 받아 응답 JSON/XML을 만들고 인증을 확인한다. Application (src/application/) — 주방장. 주문서를 받아서 레시피(도메인)대로 요리 과정을 진행한다. 유스케이스를 조합한다("단어 조회 + 세션 생성 + 저장"). Domain (src/domain/) — 레시피북. "파스타에 소금은 몇 g" 같은 순수한 규칙과 지식 자체다. 비즈니스 규칙이 여기에 있다("점수 = 정답수/전체 × 3000"). Infrastructure (src/infrastructure/) — 냉장고, 오븐, 접시. 실제 재료를 꺼내고 보관하는 물리적 장비다. MySQL 쿼리 실행, Redis 캐시, 이벤트 발행이 여기서 일어난다. 핵심 규칙: 위 층은 아래 층을 부를 수 있지만, 아래 층은 위 층을 몰라야 한다. 레시피(Domain)가 "어떤 냉장고를 쓸지"를 알 필요는 없다. 이렇게 분리하면 냉장고를 바꿔도(MySQL에서 PostgreSQL로) 레시피는 그대로 쓸 수 있다.

폴더 구조 전체 지도

src/
├── main.py                    # 서버 시작점
├── config.py                  # 설정 파일 읽기
├── domain/                    # 비즈니스 규칙 (순수 로직)
│   ├── shared/                # 모든 도메인이 공유하는 기반 코드
│   ├── content/               # "학습 콘텐츠" 도메인 (단어, 퀴즈)
│   └── study/                 # "학습 활동" 도메인 (세션, 점수, 미션)
├── application/               # 유스케이스 조합
│   └── study/                 # 보카 학습 서비스 (VocaService)
├── infrastructure/            # 기술 구현 (DB, 캐시, 이벤트)
│   ├── database/              # MySQL 연결, 리포지토리 구현
│   ├── cache/                 # Redis 캐시
│   └── events/                # 이벤트 핸들러
└── presentation/              # HTTP 요청/응답 처리
    ├── api/v1/                # 새 JSON API
    ├── api/legacy/            # 구 앱용 XML API
    ├── schemas/               # 요청/응답 형태 정의
    └── dependencies/          # 인증, 의존성 주입
content와 study는 서로 다른 세계(Bounded Context)다. 서로의 DB 테이블을 직접 JOIN하지 않고, 필요하면 ID만 참조한다.

데이터가 흐르는 순서

사용자가 "단어 학습 시작" 버튼을 눌렀을 때 데이터가 어떤 경로로 흘러가는지 따라가 보자. POST /api/v1/service/study/voca/mode 요청이 오면: 1. Presentation — service_voca_router.py가 요청을 받아 VocaService.view_mode()를 호출한다. 2. Application — voca_service.py가 일을 조합한다. 셀 정보 조회, 학습 세션 생성, 단어 목록 조회, 퀴즈 목록 조회, 결과를 DTO로 묶어 반환. 3. Domain — StudySession.start()가 호출되어 새 세션 객체가 만들어진다. 비즈니스 규칙이 여기서 적용된다. 4. Infrastructure — 세션 객체를 MySQL DB에 INSERT한다. UnitOfWork.commit()이 호출되면 트랜잭션이 완료되고 도메인 이벤트가 발행된다. 5. Presentation — 서비스가 돌려준 DTO를 JSON 응답으로 바꿔서 앱에 보낸다.

핵심 파일별 해설

src/main.py — 서버의 전원 스위치. DB 연결, 설정 로딩, 이벤트 핸들러 등록을 하고, URL과 함수를 매핑한다. src/config.py — settings.yaml에서 DB 주소, Redis 주소, API 설정 등을 읽어온다. 환경 변수로 덮어쓸 수 있어서 개발/운영 환경마다 다른 값을 줄 수 있다. src/domain/study/study_session_entity.py — 핵심 중의 핵심. 학습 세션 1회를 나타내는 클래스다. start()(학습 시작), submit_quiz()(퀴즈 채점), clear()(학습 완료) 세 가지 핵심 동작이 있다. 
# 학습 시작
session = StudySession.start(member_id=1, cell_idx=100, ...)

# 퀴즈 채점 (점수 계산, 경험치 부여, 부정행위 체크)
outcome = session.submit_quiz(quiz_result, abuse_limited=False)

# 학습 완료 (상태를 CLEARED로, 달성률 계산)
summary = session.clear()
src/domain/study/voca_scoring.py — "정답 몇 개 맞으면 몇 점" "경험치 상한은 3000" 같은 순수한 수학 공식이 들어 있다. src/application/study/voca_service.py — 지휘자 역할. 도메인 규칙들을 순서대로 조합한다. "콘텐츠 조회, 세션 생성, DB 저장, 이벤트 발행" 이 흐름을 만든다. src/domain/shared/ 공통 부품들: - base_entity.py: 모든 엔티티의 부모 클래스. 모든 문서에 있는 "문서번호" 칸 같은 역할. - events.py: 이벤트 시스템. "주문 완료!" 외치면 주방이 듣는 구조. - repository.py: 저장소 인터페이스(규격만). 실제 냉장고는 infrastructure에 있다. - unit_of_work.py: 트랜잭션 관리. "이 작업들은 다 되거나, 다 안 되거나" 보장한다.

코드 읽는 순서 추천

파이썬 초보라면 이 순서로 읽으면 가장 자연스럽다. 1. config.py — 짧고 주석이 잘 달려 있어서 감을 잡기 좋다. 2. domain/study/voca_scoring.py — DB도 없고 웹도 없는 순수 계산 코드. 파이썬 문법 익히기에 최고. 3. domain/study/study_session_entity.py — start(), submit_quiz(), clear() 세 메서드가 이 서비스의 전부다. 4. application/study/voca_service.py — 도메인 규칙들을 어떤 순서로 불러서 유스케이스를 만드는지 본다. 5. presentation/api/v1/service/service_voca_router.py — 34줄짜리 진입점. HTTP 요청이 서비스 호출로 변환되는 과정. 6. main.py — 전체를 연결하는 부트스트랩. 모든 조각이 어떻게 조립되는지 전체 그림 확인. tests/ 폴더의 테스트 코드도 같이 읽어보면 좋다. 테스트는 "이 코드를 이렇게 쓰면 이런 결과가 나와"를 보여주는 사용 설명서나 마찬가지다.

프로젝트 도구 정리

FastAPI — 웹 서버 프레임워크. 식당의 주방 시스템 전체. SQLAlchemy — DB를 파이썬 코드로 다루기. SQL 직접 안 쓰고 파이썬으로 DB 조작. Pydantic — 데이터 형태 검증. "이 칸은 숫자만 들어와야 해" 자동 체크. Alembic — DB 테이블 구조 변경 관리. 테이블에 컬럼 추가할 때 이력 관리. uv — 패키지 관리(pip 대체). 필요한 라이브러리 설치/관리. Docker — MySQL, Redis를 한번에 실행. DB 설치 안 해도 docker compose up 하면 끝. Ruff — 코드 스타일 검사. 맞춤법 검사기(코드 버전). pytest — 테스트 실행. 코드가 제대로 동작하는지 자동 확인.

로컬에서 서버 띄우기

# 파이썬과 도구 설치 (최초 1회)
brew install uv
uv python install 3.12
uv venv --python 3.12 && uv sync --extra dev

# 설정 파일 복사
cp settings.yaml.example settings.yaml

# MySQL + Redis 실행 (Docker 필요)
docker compose up -d

# 서버 확인
curl localhost:8000/health

# 테스트 / 린트 / 타입 검사
uv run pytest
uv run ruff check .
uv run mypy src
DDD 4-Layer 구조가 처음에는 복잡해 보이지만, 결국 "각자 자기 일만 하자"는 원칙이다. 레시피(Domain)는 순수한 규칙만, 주방장(Application)은 조합만, 냉장고(Infrastructure)는 저장만, 카운터(Presentation)는 전달만. 이 구조를 익히면 어떤 DDD 프로젝트를 만나도 코드를 읽을 수 있다.
