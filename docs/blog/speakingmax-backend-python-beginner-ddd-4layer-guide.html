SpeakingMax 백엔드 완전 해부 — 파이썬 왕초보를 위한 DDD 4-Layer 가이드

파이썬을 하나도 모르는 사람도 이해할 수 있도록, wb-speakingmax-backend 프로젝트의 구조를 처음부터 끝까지 풀어서 설명한다. 이 프로젝트는 **SpeakingMax**라는 영어 학습 앱의 백엔드 서버다. "코드를 열었는데 뭐가 뭔지 하나도 모르겠다"는 사람을 위한 글이다. ## SpeakingMax — 이 앱이 뭘 하는 거야? SpeakingMax는 영어 회화 학습 앱이다. 사용자가 영상을 보고, 단어를 외우고, 퀴즈를 풀면서 영어를 배운다. 이 백엔드 서버가 처리하는 핵심 기능은 다섯 가지다: - 영상 콘텐츠(에피소드, 시즌) 제공 - 단어(`VocaWord`) 학습 — 학습 모드, 피드백, 요약 - 퀴즈 채점과 점수 계산 - 일일 미션(`DailyMission`) 관리 - 학습 세션(`StudySession`) 상태 추적 ## 기술 스택 이 프로젝트에서 사용하는 도구들이다. 지금 당장 다 알 필요는 없다. "이런 게 있구나" 정도로 훑어보면 된다. - **Python 3.12** — 프로그래밍 언어 - **FastAPI** — 웹 프레임워크. API 서버를 만들어주는 도구 - **SQLAlchemy** — ORM. DB 테이블을 파이썬 객체로 다루게 해주는 도구 - **aiomysql** — MySQL 비동기 드라이버 - **Redis** — 캐시. 자주 쓰는 데이터를 메모리에 저장해서 빠르게 꺼내는 곳 - **Pydantic** — 데이터 검증. API로 들어오는 데이터가 올바른지 자동으로 확인 - **Alembic** — DB 마이그레이션. 데이터베이스 구조 변경을 버전 관리 - **uv** — 패키지 관리자. pip보다 훨씬 빠른 최신 도구 - **Docker** — 컨테이너. 어디서든 같은 환경으로 실행할 수 있게 포장 ## DDD 4-Layer 아키텍처 — 식당에 비유하면 이 프로젝트는 **DDD(Domain-Driven Design) 4계층 아키텍처**를 사용한다. 처음 들으면 복잡하게 느껴지지만, 식당에 비유하면 단번에 이해된다. **Presentation (표현 계층) = 홀 직원** 손님(클라이언트)의 주문을 받고, 완성된 음식을 갖다주는 역할이다. 코드에서는 API 라우터가 이 역할을 한다. **Application (응용 계층) = 주방장** 직접 요리하지 않는다. 레시피를 보고, 누구한테 뭘 시킬지 지시만 한다. 코드에서는 서비스 클래스가 이 역할을 한다. **Domain (도메인 계층) = 레시피북** "닭볶음탕에는 간장 3스푼, 고추장 1스푼"처럼 비즈니스 규칙이 적혀있는 곳이다. 코드에서는 엔티티와 도메인 서비스가 이 역할을 한다. 이 프로젝트에서 **가장 중요한 계층**이다. **Infrastructure (인프라 계층) = 식재료 창고** 식재료를 꺼내오고, 보관하는 일을 담당한다. 코드에서는 DB 접근, 외부 API 호출 등을 처리한다. 핵심 원칙: **비즈니스 규칙은 반드시 Domain 계층에만 둔다.** 주방장(Application)은 레시피(Domain)를 보고 지시만 할 뿐, 레시피 자체를 바꾸지 않는다. ## 폴더 구조 — 전체 지도 프로젝트의 핵심 폴더를 하나씩 살펴보자. **루트 디렉토리:** - `pyproject.toml` — 프로젝트 설정 파일. 이름, 버전, 라이브러리 목록 - `settings.yaml` — 환경 설정. DB 주소, Redis 주소, 시크릿 키 등 - `alembic/` — DB 마이그레이션 파일들 - `docker-compose.yml` — Docker 설정 - `tests/` — 테스트 코드 **src/ 메인 소스코드:** - `main.py` — 앱의 시작점. 서버가 켜질 때 가장 먼저 실행되는 파일 - `config.py` — `settings.yaml`을 읽어와서 파이썬 객체로 바꿔주는 코드 - `containers/` — 의존성 주입(DI) 설정. 어떤 부품을 어디에 꽂을지 결정하는 곳 **src/presentation/ — 표현 계층 (홀 직원)** - `api/v1/` — API 라우터들이 모여있는 곳 - 클라이언트의 HTTP 요청을 받아서 Application 계층에 전달한다 **src/application/ — 응용 계층 (주방장)** - `study/voca_service.py` — 단어 학습 서비스. 이 프로젝트의 핵심 서비스 - Domain 객체를 가져와서 비즈니스 로직을 조합하고 실행한다 **src/domain/ — 도메인 계층 (레시피북)** - `shared/` — 공통 도구. Base Entity, Repository 인터페이스, UnitOfWork - `content/` — 콘텐츠 관련 규칙. 단어, 에피소드 등 - `study/` — 학습 관련 규칙. StudySession, VocaQuiz, DailyMission **src/infrastructure/ — 인프라 계층 (창고)** - `database/` — DB 연결 설정, SQLAlchemy 모델 정의 - `external/` — 외부 API 연동 코드 - `redis/` — Redis 캐시 설정 ## Content와 Study — 두 개의 세계 이 프로젝트는 두 개의 **Bounded Context**(경계가 있는 영역)로 나뉜다. **Content (콘텐츠)** — DB 스키마: `sm_content` 미리 준비된 식재료다. 영상, 에피소드, 시즌, 단어 데이터가 여기 들어있다. 앱에서 이 데이터를 수정하지 않는다. 읽기 전용이다. **Study (학습)** — DB 스키마: `sm_study` 주문서와 영수증이다. 사용자가 학습을 시작하고, 퀴즈를 풀고, 점수를 받는 모든 활동이 여기 기록된다. 두 세계는 **ID 참조**로만 연결된다. Content에 있는 단어의 ID를 Study에서 참조할 뿐, 직접 객체를 공유하지 않는다. 이렇게 분리하면 한쪽을 바꿔도 다른 쪽에 영향이 없다. ## 코드 읽는 순서 처음 이 프로젝트를 읽을 때 추천하는 순서가 있다. **1단계: Domain 계층부터 읽어라** 비즈니스 규칙이 다 여기 있다. "이 앱이 뭘 하는지"를 가장 빨리 파악할 수 있다. `src/domain/study/study_session_entity.py` — 학습 세션 상태 관리 `src/domain/study/voca_scoring.py` — 퀴즈 점수 계산 로직 **2단계: Application 계층 읽기** Domain의 규칙들을 어떤 순서로 조합해서 기능을 완성하는지 볼 수 있다. `src/application/study/voca_service.py` — 핵심 3가지 유스케이스 **3단계: Presentation 계층 읽기** 어떤 URL로 어떤 기능이 제공되는지 확인한다. 놀랍도록 짧다. `src/presentation/api/v1/service/service_voca_router.py` — 단 34줄 **4단계: Infrastructure 계층 읽기** DB 테이블 구조나 외부 연동 방식을 파악한다. ## Domain 계층 — 비즈니스 규칙의 심장 가장 중요한 엔티티인 `StudySession`을 살펴보자. 학습 세션의 상태를 관리하는 핵심 객체다. 상태는 READY → IN_PROGRESS → COMPLETED → CLEARED 순서로 흐른다. class StudySession(BaseEntity): # 학습 세션의 상태 전이 규칙 def start(self): if self.status != "READY": raise DomainException("시작 불가") self.status = "IN_PROGRESS" def submit_quiz(self, answers): if self.status != "IN_PROGRESS": raise DomainException("진행 중이 아님") self.score = calculate_score(answers) self.status = "COMPLETED" def clear(self): if self.status != "COMPLETED": raise DomainException("완료 상태가 아님") self.status = "CLEARED" 이 코드에서 주목할 점: - `start()`, `submit_quiz()`, `clear()` — 상태가 바뀌는 모든 규칙이 엔티티 안에 있다 - 각 메서드는 "현재 상태를 검사한 뒤 조건에 맞으면 상태를 변경한다"는 패턴을 따른다 - 비즈니스 규칙이 서비스나 컨트롤러가 아닌, **도메인 엔티티 안에 캡슐화**되어 있다 - DDD에서 이런 엔티티를 **애그리거트 루트(Aggregate Root)**라고 부른다 ## 점수 계산 — 순수한 비즈니스 로직 퀴즈 점수 계산도 Domain 계층에 있다. `MAX_CELL_SCORE`는 3000점이 최고 점수라는 뜻이다. class VocaScoringService: MAX_CELL_SCORE = 3000 # 맞은 개수 / 전체 개수 x 3000 = 최종 점수 # 예시: 8개 중 6개 정답 = 2250점 이 로직이 Service나 Controller가 아닌 Domain 계층에 있는 이유: 점수 계산은 **비즈니스 규칙**이기 때문이다. "맞은 비율에 3000을 곱한다"는 규칙은 기술적인 결정이 아니라 비즈니스 결정이다. 나중에 채점 방식이 바뀌면 이 파일만 고치면 된다. ## Application 계층 — 주방장의 지시 `VocaService`는 단어 학습의 세 가지 유스케이스를 처리한다. **viewMode** — 학습 모드 화면 단어 목록을 Content에서 가져오고, 학습 상태를 Study에서 가져와서 합쳐서 보여준다. **viewFeedback** — 퀴즈 결과 피드백 퀴즈를 채점한 뒤, 맞은 것과 틀린 것을 구분해서 보여준다. **viewSummary** — 학습 요약 전체 성적과 통계를 모아서 보여준다. Application 계층의 핵심 원칙: **자기 자신은 비즈니스 규칙을 갖지 않는다.** Domain 계층의 엔티티와 서비스를 가져와서, 순서대로 조합하고, 실행할 뿐이다. ## Presentation 계층 — 34줄의 라우터 FastAPI 라우터는 놀라울 정도로 짧다. 총 34줄에 불과하다. 라우터의 역할은 딱 세 가지다: 1. 클라이언트의 HTTP 요청을 받는다 2. Application 계층의 서비스를 호출한다 3. 결과를 JSON으로 돌려준다 모든 비즈니스 규칙은 Domain에, 조합 로직은 Application에 있기 때문에 라우터는 그저 "전달자"일 뿐이다. 그래서 이렇게 짧을 수 있다. ## Infrastructure 계층 — 기술적 뒷받침 이 계층은 실제 기술적인 구현을 담당한다. **데이터베이스 연결:** SQLAlchemy의 비동기(async) 기능으로 MySQL에 접속한다. `mapped_entity`라는 데코레이터로 도메인 엔티티와 DB 테이블을 연결한다. **스키마 분리:** `sm_content`와 `sm_study` 두 개의 스키마를 사용한다. 한 DB 안에서 논리적으로 영역을 나눠놓은 것이다. **Repository 구현:** Domain 계층에서 정의한 Repository 인터페이스를 실제로 구현한다. `AbstractCommandRepository` — 데이터를 저장하고 수정하는 역할 `AbstractQueryRepository` — 데이터를 조회하는 역할 Command와 Query를 분리하는 이 패턴을 **CQRS**라고 부른다. ## 의존성 주입 — 부품 조립 설명서 `src/containers/base_container.py`는 프로젝트의 **조립 설명서**다. "Repository 인터페이스에는 이 구현체를 꽂아라" "Service에는 이 Repository를 넘겨줘라" 이런 설정을 한 곳에서 관리한다. 이렇게 하면 나중에 DB를 MySQL에서 PostgreSQL로 바꿀 때, Domain이나 Application 코드는 건드리지 않고 Infrastructure 구현체만 교체하면 된다. ## 이벤트 시스템 이 프로젝트는 **도메인 이벤트** 패턴도 사용한다. "학습이 완료되었다"는 이벤트가 발생하면, 그 이벤트를 듣고 있는 핸들러가 자동으로 반응한다. 예를 들어 학습 완료 이벤트가 발생하면 일일 미션 진행률을 자동으로 업데이트할 수 있다. `UnitOfWork`가 commit할 때 모아둔 이벤트를 한꺼번에 발행한다. 이렇게 하면 "학습 완료 처리"와 "미션 업데이트"가 느슨하게 연결되어, 한쪽을 바꿔도 다른 쪽에 영향이 없다. ## 정리 - **DDD 4-Layer**: Presentation → Application → Domain → Infrastructure, 각 계층은 자기 역할만 한다 - **Domain이 핵심**: 모든 비즈니스 규칙은 Domain 계층에만 존재한다 - **Content/Study 분리**: 콘텐츠와 학습 데이터는 각자의 영역에서 독립적으로 관리된다 - **ID 참조**: 두 영역은 ID로만 연결된다. 직접 객체를 공유하지 않는다 - **Repository 패턴**: 인터페이스는 Domain에, 구현은 Infrastructure에 둬서 기술 변경에 유연하다 - **코드 읽는 순서**: Domain → Application → Presentation → Infrastructure
