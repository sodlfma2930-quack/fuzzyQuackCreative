DDD START! 정리 — 응용 서비스와 표현 영역의 역할 분리 (Chapter 6)

도메인 모델이 아무리 잘 설계되어도, 사용자의 요청을 받아서 도메인을 실행하고 결과를 돌려주는 **접점**이 필요하다. 그 접점이 **표현 영역**과 **응용 서비스**다. 6장은 이 두 영역의 역할과 경계, 그리고 자주 범하는 실수들을 정리한다. ## 표현 영역과 응용 영역 **표현 영역**은 사용자의 요청을 해석한다. HTTP 요청 파라미터를 읽고, 세션을 관리하고, 응답 형식(HTML, JSON 등)을 결정한다. **응용 서비스**는 실제 사용자가 원하는 기능을 실행한다. 도메인 객체를 이용해서 기능을 구현하며, 표현 영역에 의존하지 않는다. 요청의 흐름: - 사용자가 요청을 보낸다 - 표현 영역이 요청을 받아 해석한다 (HTTP 파라미터 파싱, 인증 확인 등) - 응용 서비스에 기능 실행을 위임한다 - 응용 서비스가 도메인 객체를 사용해서 기능을 수행한다 - 결과를 표현 영역에 리턴한다 - 표현 영역이 결과를 사용자에게 알맞은 형식으로 변환하여 응답한다 ## 응용 서비스의 역할 응용 서비스의 핵심 역할은 도메인 객체를 사용해서 사용자의 요청을 처리하는 것이다. 직접 도메인 로직을 구현하지 않고, 도메인 모델에 위임한다. public class ChangePasswordService { @Transactional public void changePassword(String memberId, String curPw, String newPw) { Member member = findExistingMember(memberId); member.changePassword(curPw, newPw); } } 응용 서비스가 하는 일: - 리포지터리에서 애그리거트를 구한다 - 애그리거트의 도메인 기능을 실행한다 - 결과를 리턴한다 이 흐름이 전형적인 응용 서비스 구현이다. **도메인 로직은 도메인 객체에, 응용 서비스는 흐름만 조정**한다. ## 도메인 로직을 넣지 않기 응용 서비스에 도메인 로직을 넣으면 안 되는 이유는 두 가지다: - **코드 중복이 발생**한다. 같은 도메인 로직을 여러 응용 서비스에서 각각 구현하게 된다. - **로직이 분산**된다. 도메인 로직이 응용 서비스와 도메인 객체에 흩어지면 코드를 이해하기 어렵고, 수정도 어려워진다. 나쁜 예 -- 응용 서비스에 도메인 로직이 들어간 경우: public class DeactivationService { public void deactivate(String memberId) { Member member = memberRepository.findById(memberId); // 도메인 로직이 서비스에 있음! if (!member.isActive()) { throw new AlreadyDeactivatedException(); } member.setStatus(Status.DEACTIVATED); member.setDeactivatedDate(LocalDateTime.now()); } } 올바른 예 -- 도메인 로직은 도메인 객체에: public class DeactivationService { public void deactivate(String memberId) { Member member = memberRepository.findById(memberId); member.deactivate(); // 도메인 로직은 Member 안에 } } ## 응용 서비스의 크기 응용 서비스 클래스를 어떤 단위로 나눌 것인가? 두 가지 방식이 있다. **방식 1: 한 클래스에 도메인의 모든 기능을 구현** public class MemberService { public void join(MemberJoinRequest req) { ... } public void changePassword(String id, String curPw, String newPw) { ... } public void initializePassword(String id) { ... } public void leave(String id, String curPw) { ... } } 장점: 한 도메인의 관련 기능이 한 곳에 모여 있어서 중복 코드를 private 메서드로 묶기 쉽다. 단점: 클래스가 커지면서 연관 없는 코드가 한 클래스에 뒤섞인다. 코드 품질이 낮아진다. **방식 2: 구분되는 기능별로 서비스 클래스를 따로 구현** public class ChangePasswordService { public void changePassword(String id, String curPw, String newPw) { ... } } 장점: 클래스별 역할이 명확하고, 코드 품질 유지가 쉽다. 단점: 클래스 개수가 많아진다. 하지만 코드 품질 면에서 이게 더 유리하다. 각 기능마다 동일한 로직을 구현하면 별도 헬퍼 클래스에 모아두면 된다: public final class MemberServiceHelper { public static Member findExistingMember(MemberRepository repo, String id) { Member member = repo.findById(id); if (member == null) throw new NoMemberException(id); return member; } } ## 응용 서비스의 인터페이스 응용 서비스에 인터페이스가 필요한가? 구현 클래스가 여러 개이거나 런타임에 교체해야 하면 인터페이스를 쓸 가치가 있다. 하지만 응용 서비스의 구현 클래스가 두 개인 경우는 매우 드물다. 인터페이스와 클래스를 따로 만들면 소스 파일만 늘어나고 전체 구조만 복잡해진다. 인터페이스가 명확하게 필요하기 전까지는 **인터페이스를 작성하지 않는 것**이 좋다. ## 메서드 파라미터와 값 리턴 응용 서비스가 제공하는 메서드는 도메인을 이용해서 사용자가 요구한 기능을 실행하는데, 이를 위해 필요한 값을 파라미터로 전달받아야 한다. 개별 값을 파라미터로 전달받는 방식: public void changePassword(String memberId, String curPw, String newPw) { ... } 별도 데이터 클래스로 전달받는 방식: public class ChangePasswordRequest { private String memberId; private String curPw; private String newPw; } public void changePassword(ChangePasswordRequest request) { Member member = findExistingMember(request.getMemberId()); member.changePassword(request.getCurrentPassword(), request.getNewPassword()); } 스프링 MVC 같은 프레임워크는 HTTP 요청 파라미터를 자바 객체로 변환하는 기능을 제공한다. 파라미터가 두 개 이상이면 별도 클래스를 만들어서 전달하는 것이 편리하다. 응용 서비스의 결과를 표현 영역에서 사용해야 한다면 필요한 데이터를 리턴한다. 주문 기능을 예로 들면, 주문 후 주문번호를 리턴해야 표현 영역에서 주문 상세 링크를 보여줄 수 있다. @Transactional public OrderNo placeOrder(OrderRequest orderRequest) { OrderNo orderNo = orderRepository.nextId(); Order order = createOrder(orderNo, orderRequest); orderRepository.save(order); return orderNo; } ## 표현 영역에 의존하지 않기 응용 서비스의 파라미터 타입을 결정할 때 표현 영역과 관련된 타입을 사용하면 안 된다. `HttpServletRequest`나 `HttpSession`을 응용 서비스에 파라미터로 전달하면 안 된다. // 나쁜 예 -- 표현 영역에 의존! public class AuthenticationService { public void authenticate(HttpServletRequest request) { String id = request.getParameter("id"); String password = request.getParameter("password"); if (checkIdPasswordMatching(id, password)) { HttpSession session = request.getSession(); session.setAttribute("auth", new Authentication(id)); } } } 이렇게 하면: - 응용 서비스를 단독으로 테스트하기 어려워진다 - 표현 영역의 구현이 변경되면 응용 서비스도 함께 변경해야 한다 - 응용 서비스가 표현 영역의 역할까지 대신하게 된다 응용 서비스의 파라미터와 리턴 타입으로 **표현 영역의 구현 기술을 사용하지 않는 것**이 원칙이다. ## 트랜잭션 처리 응용 서비스의 중요한 역할 중 하나가 트랜잭션 관리다. 회원 가입에 성공했다고 하면서 실제로 DB에 회원 정보를 삽입하지 못하면 고객은 로그인을 할 수 없게 된다. 이런 트랜잭션 관련 문제를 관리하는 것이 응용 서비스의 중요한 역할이다. public class ChangePasswordService { @Transactional public void changePassword(ChangePasswordRequest request) { Member member = findExistingMember(request.getMemberId()); member.changePassword(request.getCurrentPassword(), request.getNewPassword()); } } 프레임워크가 제공하는 트랜잭션 기능을 적극 사용하는 것이 좋다. 스프링의 `@Transactional`을 붙이면 RuntimeException이 발생하면 롤백하고 그렇지 않으면 커밋한다. ## 도메인 이벤트 처리 응용 서비스의 역할 중 하나는 도메인 영역에서 발생시킨 이벤트를 처리하는 것이다. 예를 들어, 암호 변경 후에 '암호 변경됨' 이벤트를 발생시킬 수 있다. public class Member { public void initializePassword() { String newPassword = generateRandomPassword(); this.password = new Password(newPassword); Events.raise(new PasswordChangedEvent(this.id, password)); } } 응용 서비스는 이 이벤트를 받아서 후처리를 한다. 암호 초기화의 경우, 이벤트가 발생하면 변경된 암호를 이메일로 발송하는 이벤트 핸들러를 등록할 수 있다. 이벤트를 사용하면 코드가 다소 복잡해지지만 도메인 간의 의존성이나 외부 시스템에 대한 의존을 낮춰주는 장점이 있다. ## 값 검증 값 검증은 표현 영역과 응용 서비스 두 곳에서 수행할 수 있다. **표현 영역**: 필수 값, 값의 형식, 범위 등을 검증한다. **응용 서비스**: 데이터의 존재 유무와 같은 논리적 오류를 검증한다. // 표현 영역 @Controller public class Controller { @RequestMapping public String join(JoinRequest joinRequest, Errors errors) { new JoinRequestValidator().validate(joinRequest, errors); if (errors.hasErrors()) return formView; try { joinService.join(joinRequest); return successView; } catch(DuplicateIdException ex) { errors.rejectValue(ex.getPropertyName(), "duplicate"); return formView; } } } 표현 영역에서 필수 값과 형식을 검사하면, 응용 서비스는 아이디 중복 여부와 같은 논리적 오류만 검사하면 된다. 이렇게 역할을 나누면 검증 코드가 중복되지 않는다. ## 권한 검사 권한 검사는 표현 영역, 응용 서비스, 도메인 세 곳에서 수행할 수 있다. **표현 영역**: 인증된 사용자인지 여부를 검사한다. 서블릿 필터를 이용해서 인증 정보를 생성하고 접근을 제어한다. **응용 서비스**: URL 만으로 접근 제어를 할 수 없는 경우 메서드 단위로 권한 검사를 수행한다. public class BlockMemberService { @PreAuthorize("hasRole('ADMIN')") public void block(String memberId) { Member member = memberRepository.findById(memberId); if (member == null) throw new NoMemberException(); member.block(); } } **도메인**: 개별 도메인 객체 수준의 권한이 필요한 경우. 게시글 삭제는 본인 또는 관리자만 가능한 경우 등. public class DeleteArticleService { public void delete(String userId, Long articleId) { Article article = articleRepository.findById(articleId); checkArticleExistence(article); permissionService.checkDeletePermission(userId, article); article.markDeleted(); } } ## 조회 전용 기능과 응용 서비스 5장에서 조회 전용 모델과 DAO를 다뤘다. 서비스에서 이들 조회 전용 기능을 사용하게 되면, 서비스 코드가 단순히 조회 전용 기능을 호출하는 것으로 끝나는 경우가 많다. public class OrderListService { public List getOrderList(String ordererId) { return orderViewDao.selectByOrderer(ordererId); } } 서비스에서 수행하는 추가적인 로직이 없을뿐더러 조회 전용 기능이어서 트랜잭션이 필요하지도 않다. 이런 경우 응용 서비스를 만들지 않고 표현 영역에서 바로 조회 전용 기능에 접근해도 된다. @Controller public class OrderController { private OrderViewDao orderViewDao; @RequestMapping("/myorders") public String list(ModelMap model) { String ordererId = SecurityContext.getAuthentication().getId(); List orders = orderViewDao.selectByOrderer(ordererId); model.addAttribute("orders", orders); return "order/list"; } } 응용 서비스가 존재해야 한다는 강박관념을 가지지 않는 것이 좋다. 응용 서비스가 사용자 요청 기능 실행에 별다른 기여를 하지 못한다면 굳이 서비스를 만들지 않아도 된다.
